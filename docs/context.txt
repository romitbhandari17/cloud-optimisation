# 1. Workstream A — AWS Cloud Cost Optimisation

This should be a structured 10-step engineering process.

## Step 1. AWS Account Discovery and Inventory

Repeatable engineering task

First, understand what the customer has deployed.

| Activity                      | AWS service/tool               |
| ----------------------------- | ------------------------------ |
| Discover AWS accounts         | AWS Organizations              |
| Inventory EC2 instances       | AWS Config / Resource Explorer |
| Discover RDS databases        | RDS APIs                       |
| Identify S3 buckets           | S3 APIs                        |
| Identify Lambda functions     | Lambda APIs                    |
| Discover ECS/EKS workloads    | ECS/EKS APIs                   |
| Identify networking resources | VPC APIs                       |
| Discover unused resources     | Trusted Advisor / Config       |

Engineer deliverable: Infrastructure inventory report.

It should contain:

- AWS account and region
- Service and resource name
- Resource type
- Instance size/configuration
- Current state
- Monthly cost
- Utilisation metrics
- Environment (production, staging, development)

This should be automated using Python and AWS SDK (Boto3) wherever possible.

## Step 2. Cost Analysis

Understand where the money is going.

| Activity                         | AWS service                |
| -------------------------------- | -------------------------- |
| Monthly service-wise expenditure | AWS Cost Explorer          |
| Detailed cost breakdown          | AWS CUR / Data Exports     |
| Cost by account                  | Cost Explorer              |
| Cost by application              | Cost allocation tags       |
| Cost anomaly detection           | AWS Cost Anomaly Detection |
| Budget monitoring                | AWS Budgets                |

Engineers should classify expenditure into:

1. Compute
2. Storage
3. Database
4. Networking
5. Monitoring and logging
6. AI/ML services
7. Backup and disaster recovery
8. Other managed services

Deliverable: AWS Cost Breakdown Report.

## Step 3. Compute Optimisation

This is usually one of the most important areas.

| Resource     | What engineers should check      | Potential action                 |
| ------------ | -------------------------------- | -------------------------------- |
| EC2          | CPU, memory, network utilisation | Right-size                       |
| EC2          | Instance family suitability      | Change instance family           |
| EC2          | Underutilised instances          | Downsize                         |
| EC2          | Idle instances                   | Stop or terminate after approval |
| ECS          | CPU/memory reservations          | Tune task sizing                 |
| EKS          | Node utilisation                 | Optimise node groups             |
| Lambda       | Memory, duration, invocations    | Tune memory and execution        |
| Auto Scaling | Scaling configuration            | Improve scaling policies         |

Important: CPU alone is not sufficient for right-sizing. Memory, network, application latency, throughput and workload patterns must also be considered.

Useful tools:

- Compute Optimizer
- CloudWatch
- Trusted Advisor
- Cost Explorer

## Step 4. Database Optimisation

| Resource    | Engineering activity                |
| ----------- | ----------------------------------- |
| RDS         | Analyse CPU, memory and connections |
| RDS         | Identify oversized DB instances     |
| RDS         | Review storage configuration        |
| RDS         | Identify idle databases             |
| Aurora      | Analyse capacity utilisation        |
| DynamoDB    | Review provisioned vs on-demand     |
| ElastiCache | Identify underutilised clusters     |
| Redshift    | Analyse cluster utilisation         |

Additional checks:

- Connection pooling
- Query performance
- Index optimisation
- Read replicas
- Storage growth
- Backup retention
- Database serverless options

Deliverable: Database optimisation recommendations.

## Step 5. Storage Optimisation

| Resource        | What to check                          |
| --------------- | -------------------------------------- |
| S3              | Storage classes and lifecycle policies |
| EBS             | Unattached volumes                     |
| EBS             | Oversized volumes                      |
| EBS             | Unused snapshots                       |
| EFS             | Storage growth and access patterns     |
| AWS Backup      | Retention policies                     |
| CloudWatch Logs | Log retention                          |

For S3, specifically check:

- Frequently accessed data
- Infrequently accessed data
- Archive candidates
- Duplicate data
- Incomplete multipart uploads
- Lifecycle transition policies

## Step 6. Networking Cost Optimisation

This is often overlooked.

Check:

- NAT Gateway expenditure
- Data transfer between Availability Zones
- Internet data transfer
- Cross-region data transfer
- Load balancer utilisation
- VPC endpoints
- CloudFront caching
- Inter-region traffic

For example, unnecessary cross-AZ traffic between ECS and RDS can increase monthly expenditure.

## Step 7. Pricing Model Optimisation

Review:

- On-Demand vs Reserved Instances
- Savings Plans
- Spot Instances
- EC2 commitment coverage
- RDS Reserved Instances
- Graviton migration opportunities

Do not recommend commitments until workload stability and historical usage are understood.

## Step 8. Non-Production Environment Optimisation

This is an excellent repeatable opportunity.

Check:

- Development environments running 24/7
- Staging environments running overnight
- Unused QA environments
- Temporary EC2 instances
- Unused databases
- Old snapshots and test data

Implement automated schedules using EventBridge and Lambda or Systems Manager.

## Step 9. Security and Architecture Review

Cost optimisation should not compromise reliability or security.

Review:

- AWS Well-Architected Framework
- IAM permissions
- Publicly accessible resources
- Encryption
- Backup and recovery
- High availability
- Disaster recovery
- Logging and monitoring

## Step 10. Implementation and Savings Validation

Every recommendation should have:

| Field                     | Example                     |
| ------------------------- | --------------------------- |
| Resource                  | EC2 instance                |
| Current configuration     | m6i.2xlarge                 |
| Recommended configuration | m6i.xlarge                  |
| Current monthly cost      | Actual measured cost        |
| Expected savings          | Estimated amount            |
| Risk                      | Medium                      |
| Implementation            | Resize instance             |
| Approval                  | Customer approval           |
| Validation                | Compare post-change metrics |

The most important point: Measure actual savings after implementation. Recommendations are not savings until they are implemented and validated against an appropriate baseline.

# 2. Workstream B — Agentic AI Implementation on AWS

This is where Cloudineer can differentiate itself from traditional AWS cost optimisation and managed services companies.

Instead of merely reviewing cloud resources, you identify operational workflows that can be automated using AI agents.

I would create a standard Agentic AI discovery and implementation process.

## Step 1. Identify Automation Opportunities

The engineer interviews the customer's CloudOps, DevOps, Infrastructure and application teams.

Look for repetitive activities.

| Area           | Existing manual activity         | Agentic AI opportunity           |
| -------------- | -------------------------------- | -------------------------------- |
| CloudOps       | Investigating high CPU           | Cloud troubleshooting agent      |
| FinOps         | Reviewing monthly AWS bills      | Cost analysis agent              |
| DevOps         | Investigating failed deployments | Deployment troubleshooting agent |
| Security       | Reviewing security findings      | Security assessment agent        |
| Infrastructure | Checking unused resources        | Resource optimisation agent      |
| Monitoring     | Investigating CloudWatch alarms  | Incident investigation agent     |
| Backup         | Checking backup failures         | Backup compliance agent          |
| Database       | Investigating slow queries       | Database analysis agent          |
| Governance     | Checking resource compliance     | Compliance monitoring agent      |

Deliverable: Agentic AI Opportunity Assessment.

## Step 2. Select and Prioritise Use Cases

Not everything needs an agent.

Classify opportunities into three categories:

- Deterministic automation: Lambda, Python, Systems Manager, Step Functions.
- AI-assisted workflows: LLM analyses findings and provides recommendations.
- Agentic workflows: Agents reason across tools, gather evidence, choose next steps and execute permitted actions.

For example:

| Use case                         | Recommended implementation    |
| -------------------------------- | ----------------------------- |
| Stop EC2 at 8 PM                 | EventBridge + Lambda          |
| Identify oversized EC2           | Compute Optimizer + AI agent  |
| Investigate CPU spikes           | CloudWatch + Bedrock agent    |
| Troubleshoot deployment failures | Logs + Bedrock agent          |
| Investigate security findings    | Security Hub + Bedrock agent  |
| Recommend database optimisation  | CloudWatch + RDS metrics + AI |

This distinction is important. You don't want to use expensive LLM calls for tasks that a simple Python script can perform.

## Step 3. Design the Agent Architecture

Standardise the architecture so engineers don't reinvent it for every customer.

## Cloudineer Agentic AI Reference Architecture

Trigger / Input Layer

CloudWatch · EventBridge · API · Ticket · Scheduled Job

Agent Orchestration

## Amazon Bedrock Agents

Reasoning · Tool selection · Planning · Multi-step workflows

Action Groups

Lambda · Python · APIs

Knowledge & Context

S3 · Knowledge Bases · OpenSearch

AWS Execution Layer

EC2 · ECS · RDS · CloudWatch · Cost Explorer · Systems Manager · Security Hub

Approval, Audit & Monitoring

Step Functions · SNS · CloudTrail · DynamoDB · CloudWatch

One architectural principle: agents should not receive unrestricted AWS credentials. Use narrowly scoped IAM roles, allowlisted actions, validation, approval gates and auditable execution.

## Step 5. Implement the Agent Workflow

For each agent, the AWS Engineer should follow the same implementation checklist.

1. Define the business problem.
2. Define the agent's responsibility and boundaries.
3. Identify required AWS APIs.
4. Define the IAM execution role.
5. Implement Lambda action groups.
6. Define the agent instructions and tools.
7. Configure knowledge/context sources if needed.
8. Implement orchestration and approval workflows.
9. Add audit logs and execution tracking.
10. Test with historical and simulated scenarios.
11. Evaluate accuracy, safety and cost.
12. Deploy to production with monitoring.

## Step 6. Establish Agent Governance

This is particularly important when the agent can make changes to infrastructure.

| Agent action                | Permission model   |
| --------------------------- | ------------------ |
| Read CloudWatch metrics     | Automatic          |
| Analyse AWS costs           | Automatic          |
| Generate recommendations    | Automatic          |
| Generate remediation plan   | Automatic          |
| Stop EC2 instances          | Approval initially |
| Resize EC2                  | Approval           |
| Modify security groups      | Approval           |
| Delete resources            | Explicit approval  |
| Modify production databases | Explicit approval  |

You can gradually introduce autonomy based on the customer's risk appetite and successful evaluation results.

The repository should be customer-configurable, not customer-specific code forks. Keep account IDs, regions, thresholds, exclusions, approval policies and resource tags in configuration files.

# 5. Define Roles and Responsibilities

You don't want every AWS Engineer making architectural decisions independently.

I would use three levels.

| Role                    | Responsibilities                                                                  |
| ----------------------- | --------------------------------------------------------------------------------- |
| AWS Solutions Architect | Assessment strategy, architecture decisions, prioritisation, customer discussions |
| AWS Cloud Engineer      | Resource discovery, cost analysis, optimisation implementation                    |
| AI/Automation Engineer  | Bedrock agents, Lambda integrations, workflows, evaluations and monitoring        |

For a small engagement, one engineer may perform multiple roles.

Your role as Cloud Architect: Review the assessment, approve the optimisation roadmap, select agentic AI use cases and conduct architecture reviews.
